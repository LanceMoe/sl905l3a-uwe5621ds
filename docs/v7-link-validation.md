# v7 实机短测记录

资料：`cm311-linktest-20261017-044205-invqvb6k.tar.gz`，2026-10-17，
CM311-1a YST / UWE5621DS，`6.18.37-ophub`，PORT_VERSION=7。

本轮初始化、关联、DHCP 成功，`iw link` 查询成功，测试前后平台驱动保持绑定。
所有探测指定 `-I wlan0`，原始 MTU 为 1400，本轮没有修改 MTU。

超过 MTU 的原始输出为 `ping: local error: message too long, mtu=1400`。
虽然 ping 同时打印 100% packet loss，这些探测未发到无线链路，不能当作无线丢包。

## 启动与收发证据

- 历史加载日志在内核时间 104.691706 秒记录启动同步地址 `0x40525fa0` 读取 `-84`，
  随后 `startup sync read retry 1/2`，下一次读到 `0xf0f0f0f1`，
  之后完成校准、firmware-ready、Wi-Fi API 与 INI 初始化。有限重读在本轮确实起效；
  不能据此证明所有启动 I/O 错误都能恢复。
- 测试前后 SDIO IRQ 195→222，包读取尝试 644→793，写入尝试 103→131；
  `sdio_packet_errors` 与 `sdio_rx_no_progress` 均保持 0。
- `sdio_rx_poll_timeouts` 448→569 是兜底等待到期次数，不等于丢包次数。
- 123.331435 秒收到 `WIFI_CMD_ADDBA_REQ` 固件回复，状态 reason=2。
  对照源码 `enum addba_req_result`，该值为协商超时。驱动收到回复并清除该 TID 的
  BA 标志，随后 `WIFI_CMD_POWER_SAVE` 也有回复；这与 v5 的主机等待命令超时、
  CP2 复位不同。保留此异常继续观察，尚不能归因于 AP、空口或固件中的某一方。
- 测试后网卡 RX errors=0、TX errors=0，RX dropped=2 是累计值；
  需要对比长期增量，不能等同于此次 ICMP 丢包。

整个采集仅约 9.6 秒，每个可发送包长每个目标只有两包。
这证明 MTU 1400 下基本双向收发成功，不能证明长期稳定、吞吐或 MTU 1500 支持。
暂不根据这份短测继续修改驱动，应在原 v7 连接上持续观察。

后续结果见 [十分钟持续测试](v7-soak-validation.md)：连接保持，但出现约 2% 丢包和明显延迟波动。
