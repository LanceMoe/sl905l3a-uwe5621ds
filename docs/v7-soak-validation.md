# v7 十分钟持续测试记录

资料：`cm311-linktest-20261017-114239-awh2dx8n.tar.gz`，2026-10-17。
`6.18.37-ophub`，PORT_VERSION=7，采集脚本 v3。

现有 wlan0 连接上，同时向网关及公网各每秒发送一个禁止分片的 ICMP 探测，
payload 1372，IPv4 总长 1400，保持 MTU 1400。两个 ping 自行结束，
没有被采集器强制终止。持续探测约 601.3 秒，完整采集约 607.5 秒。

| 目标 | 发送 / 收到 | 丢包 | RTT 最小 / 平均 / 最大 |
| --- | --- | --- | --- |
| 网关 172.16.64.1 | 600 / 589 | 1.83% | 2.388 / 142.057 / 472.101 ms |
| 公网 1.1.1.1 | 600 / 586 | 2.33% | 3.343 / 139.865 / 496.708 ms |

网关收到的 589 包中，172 包 RTT 达到 400 ms；中位数 24.3 ms，
90 分位约 432 ms。公网中位数 22.5 ms，90 分位约 412 ms。
局域网网关同样出现丢包和较大延迟，公网路径不能单独解释现象；
也不能仅凭 ICMP 断定是驱动、AP、空口还是省电机制中的某一项导致。

## 驱动与连接状态

- 测试前后 `iw link` 均成功，保持连接同一 AP，信号约 -57→-55 dBm。
- 每 30 秒的快照中，SDIO 收发计数持续增加，`sdio_packet_errors` 与
  `sdio_rx_no_progress` 始终为 0，没有接收停止或错误计数增长。
- 起止快照 SDIO IRQ 8567→12351，包读取尝试 1009303→1035805，
  包写入尝试 4984→7910。读取包含空轮询，不能按包尝试数计算有效吞吐。
- 采集开始前 `dmesg` 最后时间戳为 25348.326774 秒；只统计晚于该时间的持续日志，
  避免把 `dmesg --follow` 回放的历史信息重复算入本轮。
  该范围未发现主机命令超时、CP2 复位、SDIO 错误、TX watchdog 或断开连接记录。
- 该范围有 200 次 `tx_addba failed, reason=2`，约每三秒一次；
  对照 `enum addba_req_result`，是固件回复的协商超时，不能与主机等不到回复混为一谈。
  另有 19 次接收 BA 重排定时器触发。它们是进一步排查聚合交互的线索，尚未证明与每个
  高延迟包的因果关系，不能直接据此禁用全部聚合或改重排窗口。
- 网卡累计 RX dropped 228→369，增加 141；RX/TX errors 均为 0。
  此计数还包含测试流以外的流量，不能把增加量直接等同于丢失的 ICMP 回复。

## 后续排查范围

本轮说明 v7 在持续小流量下没有重现早期卡死，但约 2% 的丢包及明显延迟波动仍需优化。
未验证吞吐、大流量、完整 MTU 1500、休眠、蓝牙或长期稳定性。

先在现有连接上读取 `iw dev wlan0 get power_save`，若为 on，可用
`iw dev wlan0 set power_save off` 暂时关闭后，以相同脚本再测十分钟。
该入口在源码 `sprdwl_cfg80211_set_power_mgmt()` 中发送 `SPRDWL_SET_PS_STATE`，
不需要修改驱动或重启，也不等同于模块的 `disable_powersave` 参数：后者控制对
固件 `EVENT_PWR_DOWN` 的处理。大量 `WIFI_CMD_POWER_SAVE` 日志也不能单独证明
802.11 省电开启，因为该命令还承载唤醒及休眠确认等子命令。

若原状态已经是 off，重复相同测试不能形成省电对照，应保留现场继续分析聚合交互，
或在明确目标后进行受控的本地 TCP 收发测试。省电只是待验证的假设，暂不改持久网络配置。

用户后续实测 `iw dev wlan0 get power_save` 为 `off`，因此不重复省电关闭对照。
逐条配对命令序号后，200 次 `WIFI_CMD_ADDBA_REQ` 的发送到回复耗时为
400.088 / 408.901 / 421.561 ms（最小 / 中位 / 最大）；
898 次 `WIFI_CMD_POWER_SAVE` 为 1.228 / 7.409 / 19.258 ms。
源码中的 ADDBA、固件唤醒及 RX BA 管理共用串行工作列表，前者同步等回复时会阻塞后续工作。
这使重复失败协商成为有依据的排查方向；仍需实机对照才能判断它对 ICMP 延迟和丢包的贡献。
下一步见 [v8 ADDBA 对照](v8-addba-comparison.md)。
